K2 Cascade

Where does the big model's advantage live?

  • Coding agents call the largest model for every step
  • Most steps are small: list a directory, read a file, run the tests
  • Question: which steps actually need a 375B, and can a small model tell?

Why K2 Horizon

Six sizes, 0.9B to 375B, fully open (IFM, Sept 3)

  • One tokenizer, one chat template, one tool-call format, one training recipe
  • So model size is the only variable
  • Our ladder: 0.9B and 3.7B on this MacBook → 375B via the IFM API
  • Each step: smallest model proposes → verifier checks → escalate on failure
  • Every attempt is one JSONL line: the trace file is the dataset

What was hard, what's next

  • Upstream llama.cpp doesn't know the architecture: compiled IFM's fork
  • No parser exists for K2's <ifm|tool_calls> format: wrote one; small models emit XML regardless of the JSON instruction
  • Caught the 375B narrating an action without calling a tool
  • Next: score the 375B's outputs token by token with the 3.7B, then a probe on the 3.7B's hidden state to predict failure before it acts. The small model knows its own limits; the external judge disappears.
